# 司机对象与运输随机事件实现计划

> 状态：**待审查**（v1 草案，尚未动代码）
> 关联：TVSOS 运输车辆调度优化与仿真系统 · 分支 fullstack-refactor

## 一、现状梳理（已通读相关代码）

**调度主链路**：`CreateOrderTask()`(每5s) → `doCreateOrderTaskBatch()`(SA分配) → `assignShipmentToVehicle()`(创建任务+占载重) → `startNextPlannedTaskForVehicle()`(Planned→Accepting并发车) → `SimulateMoving()`(每 `10s/倍速` 推进一个插值点) → `moveVehicle()` → `handlePathFinished()`(段末装/卸货切换阶段)。

**关键事实**：
- **无司机对象**：`model.Vehicle` 没有司机字段，车辆移动逻辑 `moveVehicle()` 与 `SimulateMoving()` 中完全不涉及"人"的因素。
- **车辆状态仅 3 种**（`vehicle_const.go`）：Running=1 行驶中 / Free=2 空闲 / Ready=3 待发车。**无维修状态**。前端 `vehicleList.vue` 的 `statusMap` 也只映射 1/2/3。
- **车辆移动是"逐点 tick 推进"**：`moveVehicle` 每个 tick 只前进一个插值点（50m 间距）。这是插入"暂停/减速"最干净的位置。
- **CAS 状态更新**：`UpdateVehicleStatus(id, new, old)` 乐观锁，任何状态流转必须带旧状态。
- **已有事件记录设施**：`system_event` 表 + `RecordSystemEvent()`（目前只记 startup/recovery）；`matching_log` 表记录匹配决策（M1-M4 数据源）。
- **调度可行性判定**：`isVehicleFeasible()` 只检查类型与载重，不看司机/车辆健康状况。
- **指标很完善**：9 章指标体系已落地（M/U/T/A/S/C/R/F/G），实时推送 `/ws/stats` 3s 快照。

## 二、总体设计

### 2.1 新增"司机"对象（一车一司机）

新建 `driver` 表，`vehicle` 表增加 `driver_id` 列，一车绑定一名司机（现实简化模型，支撑后续疲劳/拒单个性化）：

| 字段 | 说明 |
|---|---|
| id | 主键 |
| name / phone / license_no | 姓名/电话/驾驶证号 |
| level | 驾驶等级 1-5（影响拒单率、事故率，现实逻辑：资深司机更稳） |
| fatigue | 当前疲劳度 0~1（累计连续驾驶换算） |
| continuous_hours | 连续驾驶小时数（实时累计，到阈值触发休息） |
| rest_until | 休息截止时刻（休息中暂停移动） |
| status | 可用/休息中/请假(可选) |
| vehicle_id | 绑定车辆 |

> 现实依据：货运行业司机连续驾驶 4 小时须休息 ≥20 分钟（《道路交通安全法实施条例》第 62 条 / 货运平台通行做法）；资深司机对不划算订单拒绝率低、事故率低。

### 2.2 扩展车辆状态（回答"是否需要维修状态"）

`VehicleStatusMaintenance = 4`（维修中）。因为**车祸必然导致车辆不可用**，现状只有 3 态无法表达。需要同步改动所有依赖状态的地方（清单见 §5.3）。

## 三、随机事件类型与触发点（结合代码定位）

所有事件由**新的事件驱动循环** `RandomEventLoop()` 周期驱动 + **逐 tick 概率判定**，全部概率进配置。

### 事件 A：司机拒单（派单阶段）
- **触发点**：`startNextPlannedTaskForVehicle()` 发车前，或在 `assignShipmentToVehicle()` 创建任务前判定（推荐前者，回退更干净：此时任务仅 Planned，无路径已下发）。
- **逻辑**：读取司机 `level` → 查配置拒单概率 → `rand` 判定 → 若拒绝：
  1. 删除该 Planned OrderTask；
  2. 释放车辆 `ReservedSize`；
  3. 运单状态回退 `Queued → Sleeping`，下一轮 `CreateOrderTask` 自然重新进入 SA 分配池（**复用现有重派机制，无需新流程**）；
  4. 写 `random_event` 表（type=refuse，记 vehicle/driver/shipment）；可选写 `matching_log` 标记该次被拒；
  5. 防死循环：`driver` 表累计拒单次数，同一司机对同一运单**最多拒 N 次**（如 2 次）后强制接受。
- **现实意义**：司机对距离远/货种不合适/平台价低的单会拒，平台二次派单，拉长 T2 响应、影响 M1-M4 一次接受率。

### 事件 B：司机需要休息（运输中延后）
- **触发点**：`moveVehicle()` 每个 tick 开头。
- **逻辑**：累计 `continuous_hours`（按 tick 推进的时间增量）；超过阈值（默认 4h）且当前不在休息中 → 置 `rest_until = now + 休息时长`，写 `random_event`(type=rest)。在 `rest_until` 之前，`moveVehicle()` **直接 return 不推进**（车辆原地停留），到点自动恢复。
- **现实意义**：强制休息导致该单送达延后（迟到），车辆利用率、T1 吞吐、准时率受影响。

### 事件 C：极端天气（运输中延后）
- **触发点**：`moveVehicle()` 每个 tick，按配置概率（如每 tick 0.05%）。
- **逻辑**：触发后车辆进入"天气暂停"窗口（如 30–120 分钟，模拟封路/限行），同一套 `rest_until` 机制（或独立的 `pause_until` 字段统一处理：休息/天气/维修恢复都用它）。写 `random_event`(type=weather, severity)。
- **现实意义**：暴雨/大雾/冰雪导致运输延后，且冷藏车等时效货影响更大（可选：危化品车天气事故率更高）。

### 事件 D：车祸致车辆受损（运输中）
- **触发点**：`moveVehicle()` 每个 tick，按较低概率（如每 tick 0.02%）。
- **逻辑**：
  1. 车辆状态 CAS `Running → Maintenance`(4)，同时置 `pause_until = now + 维修时长(如 1–6h)`；
  2. 在途 OrderTask **挂起**（保持 Transporting，但 `moveVehicle` 因状态非 Running 不推进——现有 `moveVehicle` 第 52-56 行的二次校验会自动阻断，符合现状防脏逻辑）；
  3. 写 `random_event`(type=accident, severity, detail 含受损车辆/任务/预计恢复时间)；
  4. 维修到期后 CAS `Maintenance → Free`（若无挂起任务）或 `Maintenance → Ready/Running`（若有 Planned 任务则交给 `startNextPlannedTaskForVehicle` 续跑）。
- **现实意义**：车祸是最严重的随机事件，车辆短暂退出运力池（U3 在线率下降、R 系可靠性记录事故、运单严重延误，极端情况可扩展为"转运"但本期先挂起）。

> **统一暂停机制**：`moveVehicle()` 开头新增"暂停判定"——`pause_until` 未到则 return。休息/天气/维修三类延后共用这一个检查点，改动最小。

## 四、数据模型与迁移（沿用现有 `db.go` 迁移范式）

1. **新表 `driver`**：DDL 放入 `tableMigrations`（`CREATE TABLE IF NOT EXISTS`，与 metric_snapshot 等并列）。
2. **新表 `random_event`**：记录每次随机事件（供前端事件流 + R 系可靠性指标）：
   `id, event_time, event_type(refuse/rest/weather/accident), vehicle_id, driver_id, shipment_id, task_id, severity int, duration_seconds int, description, detail(text/JSON), status(pending/active/resolved)`
3. **`vehicle` 表加列**：`driver_id`（沿用 `vehicleColumnMigration` 范式），`pause_until datetime DEFAULT NULL`（统一暂停截止）。
4. **兼容存量数据**：启动迁移时若存在无司机的车辆，自动为每辆空闲/运行车辆生成一名默认司机并绑定（避免存量 20 辆车跑不起来）。
5. `scripts/schema_indicators.sql` 追加对应 DDL（保持脚本与运行迁移一致）。

## 七、指标与前端展示（对接已建 9 章面板）

- **M 章**：新增"一次接受率 = 成功派单 / (成功+拒单)"（复用 matching_log + random_event），拒单导致 T2 响应分位拉长（现有 T2 统计已自动体现）。
- **R 章**：可靠性新增"运输事故数 / 维修次数 / 平均维修时长 / 准时送达率（运输实际 vs 预估，受休息+天气+车祸共同影响）"。
- **U3 在线率**：口径调整为 `(Running+Ready+Free) / 总数`，维修中车辆剔除。
- **实时推送**：`RealtimeSummary` 增 `maintenance_vehicles`、`resting_drivers`、`random_event_count`、`recent_events[]`，3s 快照自动带出；事件流面板展示最近 N 条（类型徽标/车辆/时间/状态）。
- **可靠性事件流**：`random_event` 落库后，同 `system_event` 一样可作为 R1-R3 数据源（事故=故障，恢复=recover）。

## 八、实施顺序（建议）

1. **模型+迁移**：driver / random_event 表、vehicle 加列、常量、司机兼容数据。
2. **事件引擎骨架**：`random_event.go` 概率框架 + 暂停检查 + `RandomEventLoop()` 接入 `main.go`。
3. **事件 A 拒单**（改动最小，先打通回退闭环）。
4. **事件 B 休息**（疲劳累计 + 暂停）。
5. **事件 C 天气** + **事件 D 车祸/维修状态**（最复杂，含状态机全量核对）。
6. **调度与统计适配**（isVehicleFeasible、OnlineRate、RealtimeSummary）。
7. **前端**：状态映射、事件流面板、实时字段。
8. **测试**：单测（概率边界、暂停恢复、拒单回退、维修恢复）+ 真实跑库观察；`go vet` / `go test` / 前端 `npm run build`。

## 九、风险与注意事项

- **CAS 竞态**：维修/恢复与 `SimulateMoving` 并发，必须用现有 `UpdateVehicleStatus` CAS 链，避免把维修车误发车。
- **`moveVehicle` 二次校验**：第 52-56 行已拦截"任务在途但车非 Running"→ 车祸挂起天然安全；恢复时需正确把挂起任务续跑。
- **拒单回退必须释放 `ReservedSize`**，否则运能泄漏导致后续无车可派。
- **仿真倍速**：`RandomEventLoop` 与 `SimulateMoving` 都要乘 `GetSimulationSpeed()`，否则倍速加快后事件频率失真。
- **存量数据兼容**：迁移必须给已有车辆补司机，否则 `vehicle.driver_id` 为空、事件查询报错。
- **指标口径变更**（U3 在线率）需在报告与前端章节同步说明，避免口径不一致。
