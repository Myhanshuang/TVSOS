# TVSOS 小组汇报工作量拆分

> 拆分对象：**统计指标图表的规范化** + **实验沙箱设计** 两部分已完成工作
> 时间范围：2026-08-31 ~ 2026-09-21（提交 f21151a → 974d5d2，共 30 个提交）
> 用途：6 人小组分工汇报，每人认领一份，按 1→6 顺序讲即为完整叙事链。

## 拆分原则

1. **3 + 3 结构**：指标部分拆 3 份（设计层 / 计算层 / 展示层），沙箱部分拆 3 份（模型层 / 引擎层 / 应用层）。
2. 每份是一个**可独立讲述的闭环**：有明确问题 → 有实现 → 有可演示结果，讲完不需要别人补充背景。
3. 工作量占比按**提交数 + 代码行数**粗估，标注了依据；人力不均可跨份交换（交换建议见文末）。
4. 相邻两份之间设计了**交接句**（见各份末尾），汇报时顺序承接，不重复不遗漏。

## 第 2 份｜指标计算引擎与后端数据链路（指标·计算层）

**一句话**：把第 1 份定义的每个指标变成**每 3 秒能推送出真数**的后端实现。

### 工作内容

- **统计主链路**：`stats.go CalculateGlobalStats()`（957 行，10 个子模块）→ `realtime_stats.go BuildRealtimeDashboard()`（587 行）→ WS `/ws/stats` 推送
- **匹配质量评估（M1-M4）**：`matching_quality.go`——条件最优参考答案（固定其余指派、该单改派各车取整批成本最低者），逐单候选排名 + ground truth 回填 `matching_log`，供离线复算；精确率 / 召回率（未派单计未命中）/ F1 / MRR
- **基线对比（C1）**：同批贪心首可行基线 vs SA 成本改善百分比
- **可靠性（R1-R3）**：`reliability_stats.go` MTBF / MTTR / 可用性；**吞吐（T1）**：matching_log 计数 / 观测时长；**算法层（A2/A3）**：`solver_timing.go` SA 求解计时、`gap_evaluator.go` 小规模精确枚举 gap
- **随机事件数据源**（提交 8e5ddb9 + `司机对象与运输随机事件实现计划.md`）：拒单 / 疲劳休息 / 天气 / 车祸四类事件落库，驱动 R4-R6、F2 与事件流
- 沙箱化适配：全部指标改 experiment_id 作用域 + 虚拟时钟窗口（`scoped_repo.go` 164 行按实验过滤）

### 汇报讲点

- 全局枚举 20 辆车组合爆炸 → **条件枚举 O(单数×车数)** 的规模无关参考答案设计，及其与全局最优的强弱关系（诚实局限）
- 为什么召回率分母要包含未派单运单（否则 P=R=F1 退化失去区分度）
- 指标与落库数据（matching_log/metric_snapshot）分离设计：线上算滚动值，DB 存可回放明细

## 第 4 份｜沙箱领域模型与数据隔离（沙箱·模型层）

**一句话**：定义「沙箱 = 世界设定，实验 = 一次受控运行」的领域模型，并把运行数据按实验隔离。

- **数据隔离方案**：9 张运行表（vehicle/driver/shipment/order_task/random_event/matching_log/metric_snapshot/system_event/track_log）增加 experiment_id 维度列，**0=沙箱模板/全局、>0=实验实例**；实验启动时从车队模板实例化专属车辆/司机；POI/cargo 全局只读共享；决策记录：维度列方案 vs 每沙箱独立 schema 的取舍

## 第 5 份｜确定性数据生成与虚拟时钟运行时（沙箱·引擎层）

**一句话**：让「同一种子 → 逐 tick 完全一致」成立，这是沙箱作为实验工具的科学性根基。

### 工作内容

- **确定性数据生成器**（`sandbox/gen/generator.go` + 4 项单测）：Generate 纯函数，固定摇号序（司机等级 → 订单流泊松到达 → 天气/车祸逐 tick 摇号，车祸带 level_factor 等级修正）；输出订单流与事件脚本预生成入 `experiment_order/experiment_event` 表；DataGeneratorVersion 版本控制（v2：司机等级移入生成阶段，提交 8eae75b）
- **ExperimentRuntime**（`experiment_runtime.go` 609 行）：单实验串行生命周期（configured → generating → ready → running → finished/aborted）、单线程 masterLoop 每 tick 固定顺序执行（释放订单 → SA 派单 → 消费事件脚本 → 状态恢复 → 移动 → 快照）
- **全随机源种子化**：rt.rng 单一 RNG，SA / 司机 / 拒单全部走它；天气/车祸由预生成脚本到点消费——RNG 消费序确定 ⇒ 结果确定
- **虚拟时钟**（`virtual_clock.go`）：虚拟时间 = 起点 + tick×步长；pause_until / 阶段时间戳 / 事件时刻 / 快照时刻全部虚拟口径；倍速只改真实 tick 频率
- **环境参数接入引擎**：cost.go SetEconomyRules（油价/过路费/时薪 → Cost A 货币化里程项）、分时段速度系数（rush_hours × rush_speed_factor）
- **复现性验证**：同种子双实验总成本逐位一致（35025.80213604554 两次一致）；R1-R3/T1 观测窗口改实验生命周期

### 汇报讲点

- 为什么「预生成脚本 + 种子化运行时」双管齐下：脚本保证**输入**确定，种子保证**决策**确定
- 虚拟时钟把仿真时间与墙钟解耦——指标口径、倍速、快照都因此自洽
- 单线程 tick 顺序固定：并发引入的不确定流是复现性的天敌

## 第 6 份｜实验管理/复现/对比工具链（沙箱·应用层）

### 汇报讲点

- 导出三格式对应三种受众：HTML 给人看、Markdown 进文档、JSON 进分析脚本

「我们做了两件事：**把调度好坏量化**，和**把运行变成可复现的实验**。第 1 份讲我们选了哪些指标、为什么科学；第 2 份讲这些数怎么每 3 秒真实时算出来；第 3 份讲同一套数在运行、终态、对比三个界面怎么规范呈现。但只有一次性的运行数据，结论不可靠——所以有了沙箱：第 4 份定义世界设定与实验的领域模型；第 5 份让同种子必然同结果；第 6 份把这一切变成从建沙箱到导报告的完整研究工作流。」
